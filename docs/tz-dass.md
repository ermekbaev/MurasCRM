# ТЗ: доработки по фидбеку Дасса (ООО «Дасс», СПб)

Источник — тестирование триала dass.muras-brand.kg. Ниже: что делаем сразу
(баги + паритет-фичи, идут в продукт), и что требует отдельного скоупа.

Стек: Next.js 16 (App Router, src/), Prisma 7 (@prisma/adapter-pg), PostgreSQL,
NextAuth v5. Справочники-образец — `OrderTypeOption`.

---

## A. Баги — починить

### A1. По БИК подтягивается не тот банк / корсчёт
Код `fillFromBik` (`src/app/(dashboard)/clients/ClientsClient.tsx`) и роут
`src/app/api/dadata/bank/route.ts` на вид корректны (точная сверка `bic === query`
+ фильтр `state.status === "ACTIVE"`, endpoint `findById/bank`).
**Действия:**
1. Проверить, что `DADATA_API_KEY` задан в `.env` инстанса Дасса (в шаблоне
   `.env.dass` он отсутствовал).
2. Воспроизвести с конкретным БИК, который вводил Дасс.
3. Если данные приходят, но неверные — сверить маппинг `name.payment` vs факт;
   при необходимости брать `name.short`. Проверить `correspondent_account`.
**Готово:** ввод известного БИК подставляет верное название банка и корр. счёт.

### A2. Реквизиты не встают в шаблон счёта
**Действия:**
1. Воспроизвести: создать счёт, посмотреть, какие поля пусты.
2. Проверить, тянет ли шаблон из `CompanySettings` (в сиде Дасса пусты `kpp`,
   `director`, `accountant` — если пусты только они, это данные, а не баг).
3. Если не подставляется ничего — искать в рендере шаблона
   (`src/app/api/templates/[id]/render/route.ts`) битую привязку.
**Готово:** в счёте есть реквизиты компании (название, ИНН, КПП, р/с, банк, БИК,
директор) и клиента.

## B. Паритет-фичи — делаем в продукт

### B1. Полное и сокращённое наименование клиента
**Модель (`Client`):** добавить `fullName String?` (полное, для документов).
Текущее `name` остаётся коротким/отображаемым.
**UI:** форма клиента (ЮЛ/ИП) — второе поле «Полное наименование».
Автозаполнение по ИНН заполняет оба (DaData: `name.short_with_opf` →
короткое, `name.full_with_opf` → полное).
**Документы:** счета/акты/накладные используют `fullName` там, где нужно
юрлицо целиком; короткое — в списках/интерфейсе.
**Миграция:** добавить колонку (nullable).
**Готово:** оба поля в карточке, автозаполнение заполняет оба, документ
печатает полное наименование.

### B2. Редактируемый справочник «Источник»
Сейчас `ClientSource` — enum (хардкод). Сделать редактируемым справочником по
образцу `OrderTypeOption`.
**Модель:** `ClientSourceOption { id, code String @unique, label, sortOrder, isActive }`.
`Client.source` перевести на строковую ссылку на `code` (или `sourceId`).
**API:** CRUD `src/app/api/settings/client-sources` (GET/POST/PATCH/DELETE),
доступ ADMIN/MANAGER.
**UI:** Настройки → Источники (список + добавить/переименовать/удалить/сортировка).
Форма клиента берёт значения отсюда.
**Миграция:** создать опции из текущих значений enum, перемапить существующих
клиентов.
**Готово:** источники редактируются в настройках, в карточке — выбор из списка.

### B3. Редактируемые этапы задач
Сейчас колонки канбана завязаны на enum `TaskStatus` (хардкод). Сделать
настраиваемыми (образец — task columns в metalcrm).
**Модель:** `TaskColumn { id, name, sortOrder, color String?, isActive }`.
`Task` ссылается на `columnId` вместо enum-статуса (или доп. поле с миграцией).
**API:** CRUD `src/app/api/settings/task-columns` + reorder, доступ ADMIN/MANAGER.
**UI:** Настройки → Этапы задач (добавить/переименовать/цвет/сортировка/удалить).
Канбан рендерит колонки динамически, drag&drop между ними.
**Миграция:** создать колонки из текущих `TaskStatus`, перемапить задачи.
**Готово:** пользователь сам настраивает этапы, канбан отражает их, задачи
двигаются между настроенными этапами. (Правится на стороне клиента, без разработчика.)

### B4. Контактные лица компании
**Модель:** `ClientContact { id, clientId, name, position String?, phone String?,
email String?, telegram String?, whatsapp String?, note String?, createdAt }`,
связь many-to-one с `Client` (onDelete: Cascade).
**API:** CRUD `src/app/api/clients/[id]/contacts`.
**UI:** карточка клиента (`clients/[id]`) — блок «Контактные лица»: список +
добавить/редактировать/удалить, поля имя/должность/телефон/почта/ТГ/вацап/заметка.
**Готово:** в карточке клиента ведётся список сотрудников с контактами.

### B5. Вернуть «Поставщики» и «Оборудование» в основное меню
В редизайне уехали в Настройки (`/settings/suppliers`, `/settings/equipment`).
**UI:** `src/components/layout/Sidebar.tsx` — добавить пункты в основное меню,
ссылки на существующие роуты (страницы не трогаем, только навигацию).
**Готово:** Поставщики и Оборудование доступны из бокового меню, как в прошлой версии.

## C. Документный пакет — сделано

Реализовано целиком: C1 и C3 оказались одной работой — накладной в системе
не существовало вообще, её пришлось завести как сущность (`Waybill`,
`WaybillItem`, ТОРГ-12, печать и PDF).

### C1. Плательщик ≠ грузополучатель в накладной — готово
На товарной накладной (ТОРГ-12) уметь указывать разных: плательщик, грузополучатель,
поставщик. Актуально для клиентов с филиалами. В Bitrix этого нет — потенциальное
преимущество.
**Черновой скоуп:** в накладной выбор отдельных контрагентов на роли
«плательщик»/«грузополучатель» (из справочника клиентов), подстановка их реквизитов
в печатную форму. Уточнить набор ролей и форму документа с Дассом.

### C2. Счёт из позиций прямо внутри заявки — готово
Сейчас заявка и счёт связаны, но живут в разных местах. Дасс хочет: внутри заявки
выбрать клиента, из позиций заявки сформировать счёт, всё в одном окне.
**Черновой скоуп:** кнопка «Сформировать счёт» внутри заявки → счёт создаётся из
позиций заявки, привязан к ней, редактируется на месте. Затрагивает модель связи
заявка↔счёт и UI заявки. Обсудить желаемый флоу и объём перед оценкой.

### C3. Накладная: привязка к счёту + поле «основание» — готово
Накладная формируется на основании счёта и привязана к нему; реквизиты и позиции
подтягиваются из счёта.
**Черновой скоуп:** у накладной ссылка на счёт-основание; поле «Основание» по
умолчанию = связанный счёт (№, дата), с возможностью вручную указать другое
(например, «Договор №… от…»), если требует заказчик.

---

**Примечание.** C1–C3 — это единая цепочка документов **заявка → счёт → накладная**
(основание, привязка, плательщик/грузополучатель). Сделаны одним пакетом.

**Как получилось в итоге:**
- `Waybill`: ссылки на счёт-основание, заявку, компанию-поставщика, контрагента,
  а также отдельные `payerId` / `consigneeId` для филиальных клиентов.
- Создание накладной из счёта подтягивает позиции, контрагента, компанию и текст
  основания («Счёт № … от …»), основание можно заменить вручную.
- Печатная форма и PDF показывают три стороны: поставщик, плательщик,
  грузополучатель; при расхождении плательщика и получателя печатается пояснение.
- В заявке появилась вкладка «Документы»: связанные счета, акты и накладные плюс
  кнопка «Сформировать счёт» из позиций заявки.

## D. Документы: движок вместо бланков (продуктовая задача)

Поводом стали пожелания Дасса от 27.08.2026 — шаблоны накладной и актов «по
стандартам», свои шаблоны, список переменных, договоры и КП по кнопке.
Но задача ставится **не под одного заказчика**: CRM перепродаётся, поэтому всё
ниже проектируется как функциональность продукта.

### Главное ограничение

ТОРГ-12 и УПД — **российские** формы. Продажи идут в РФ и Казахстан, у КЗ свои
документы (накладная на отпуск запасов на сторону — форма З-2, АВР, ЭСФ),
у КР — третьи. Захардкоженный ТОРГ-12 для казахского клиента бесполезен и
потребует переписывания.

**Принцип: не «сделать ТОРГ-12», а «сделать движок документов, где ТОРГ-12 —
пресет».** Объём работы сопоставим, но результат перепродаётся без доработки
под каждого клиента.

Сейчас счёт, акт и накладная — три независимые вёрстки плюс три генератора PDF
(`invoice-pdf.ts`, `act-pdf.ts`, `waybill-pdf.ts`). Каждый новый тип документа =
ещё один такой файл. На перепродажу это не масштабируется.

### D1. Текстовые документы: договоры и КП

Самая ценная часть — универсальна как есть. У каждого клиента свои договоры и
КП; шаблонизатор снимает доработку под каждого навсегда.

**Что уже есть:** `DocumentTemplate` (типы, включая CONTRACT), подстановка
`{{переменная}}`, 37 переменных — реквизиты компании и клиента, данные заявки
и счёта, `{{order_items}}` со всеми позициями. Превью в настройках.

**Чего не хватает:**
- Кнопка «Сформировать документ» в заявке: выбор шаблона → готовый документ.
  Сейчас рендер живёт только в настройках и требует ввода id вручную.
- Вывод в PDF и сохранение результата в файлы заявки (сейчас только текст
  с возможностью скопировать).
- Тип COMMERCIAL_OFFER в enum (КП сейчас пришлось бы заводить как OTHER).

**Готово:** из заявки в два клика получается договор или КП с подставленными
реквизитами и позициями, файл лежит в заявке.

### D2. Публикация списка переменных

Поддерживается 37 переменных, в подсказке на странице шаблонов показано 5 —
остальные знает только тот, кто читал код. Это и есть «база данных функций»,
о которой спрашивал заказчик: она существует, но не опубликована.

**Скоуп:** сгруппированный справочник переменных на странице шаблонов
(компания / клиент / заявка / счёт), вставка кликом в тело шаблона.
Список формировать из одного источника, чтобы не расходился с рендером.

### D3. Конструктор бланков

Описание формы данными, а не кодом: состав и названия граф, шапка, подвал,
подписанты, показывать ли НДС. Тогда ТОРГ-12 — просто пресет, форма З-2 —
другой, а клиент правит под своего контрагента без нашего участия.

**Юридическое основание:** унифицированные формы необязательны с 2013 года
(402-ФЗ, ст. 9) — достаточно обязательных реквизитов. Настраиваемая накладная
законна. Формулировку подтвердить с бухгалтером заказчика.

**Пресеты по странам:** РФ (ТОРГ-12, счёт, акт, УПД), КЗ (З-2, АВР, ЭСФ),
КР. Новый клиент при онбординге получает пакет своей страны.

**Порядок:** новые типы делать сразу на движке; существующие три формы
оставить как есть и мигрировать позже — переписывать работающее рискованно.

### D4. УПД — отдельно и только для РФ с НДС

Форма рекомендована письмом ФНС ММВ-20-3/96@. Со **статусом 1** включает
счёт-фактуру по Постановлению 1137, где состав граф менять нельзя, иначе
покупателю могут отказать в вычете НДС. **Редактируемым делать нельзя** —
встроенный неизменяемый пресет. Статус 2 (без счёта-фактуры) — по сути та же
накладная, отдельной ценности не несёт.

### Вопросы к Дассу до оценки D3/D4

1. **Работают ли с НДС?** Если на УСН — УПД не нужен вообще, D4 отпадает.
   Спросить первым: закрывает половину объёма.
2. **Образец накладной**, которую выставляют сейчас (скан или PDF).
3. **Требует ли кто-то из их клиентов форму, прописанную в договоре?**

### Порядок реализации

1. D1 — договоры и КП (движок есть, нужен вход и выход; сразу продаваемо).
2. D2 — справочник переменных (мелко, делается заодно с D1).
3. D3 — конструктор бланков и пресеты по странам.
4. D4 — УПД, после ответа про НДС.

**Обещание заказчику.** Дассу уже сказано «накладную сделаю по ТОРГ-12 и УПД».
Отказываться не нужно — просто внутри это российский пресет движка, а не
персональная доработка. Для него результат тот же.
